### **The Automated Build Process: A Step-by-Step Guide**

This project is designed so that a single command, hugo, orchestrates a series of automated tasks. It dynamically generates the necessary configuration and asset files for both the live website and the DecapCMS admin interface. Here is a breakdown of what happens when you build the site.

---

### **Step 1: Generating the DecapCMS config.yml**

The config.yml file, which tells DecapCMS what content and fields are available, is not written by hand. It is generated by Hugo at build time.

1. **Trigger**: When Hugo builds the site, it is configured to output a file at the path /admin/config.yml.  
2. **Template Selection**: Hugo finds the specific template responsible for creating this file. In this system, it's a special partial that acts as a config generator (e.g., layouts/partials/decap-config-builder.yml).  
3. **Load Base Config**: The template first loads a base configuration file (e.g., data/decap/config\_template.yml). This file contains all the static settings: the backend connection, media folder, and definitions for collections that don't use the page builder (like "Posts" or "Authors").  
4. **Discover Section Files**: The template then scans the data/decap/sections/ directory. It reads every .yml file it finds, with each file representing the fields for a single page builder section (like hero.yml, testimonial.yml, etc.).  
5. **Inject and Merge**: The template programmatically finds the sections field within the advanced page collection of the base config. It then injects the content of all the discovered section .yml files into this field as a list of types.  
6. **Final Output**: The template combines the base config with the dynamically injected section definitions and outputs the result as a single, complete config.yml file in the public/admin/ directory.

**Result**: You never have to edit the main config.yml. Just by adding a new YAML file to data/decap/sections/, the new section automatically appears in the CMS.

---

### **Step 2: Bundling the DecapCMS Preview Components**

To provide a high-fidelity preview inside the CMS, we need to give it the code to render each section. This is also automated.

1. **Trigger**: The admin/index.html file contains a link to a JavaScript file that is processed by Hugo's asset pipeline.  
2. **Template Selection**: Hugo uses a special template that looks like a JavaScript file (e.g., assets/js/decap-previews.js.tpl) to generate the final script's source code.  
3. **Discover Preview Files**: This template scans the assets/js/decap-previews/ directory for all individual preview component files (e.g., TestimonialPreview.js).  
4. **Generate JavaScript Code**:  
   * **Imports**: For each preview file found, the template writes a JavaScript import statement at the top of the script.  
   * **Router**: It then generates a switch statement inside the main PagePreview component. This switch statement acts as a router, mapping a section's name (e.g., Testimonial) to its corresponding imported preview component.  
5. **Bundle with js.Build**: The generated source code, now full of dynamic import and switch statements, is passed to Hugo's js.Build function. This powerful tool acts like a mini-bundler (similar to Webpack or esbuild), following all the import paths and bundling everything into a single, browser-ready JavaScript file.  
6. **Final Output**: A single, optimized JavaScript file is created in the public/ directory. It contains all the code necessary for DecapCMS to render a preview of any page section.

**Result**: You never have to manually register a new preview component. Just by adding a new JS file to assets/js/decap-previews/, it is automatically bundled and made available to the CMS.

---

### **Step 3: Bundling the CSS for Site and Previews**

For the previews to look identical to the live site, they must share the exact same CSS.

1. **Trigger**: The site's main base template (baseof.html) requests the final stylesheet.  
2. **Collect Sources**: Hugo uses its asset pipeline (resources.Match) to find all .css files within the assets/css/ directory. This includes the core framework, component styles, and the section-specific styles from assets/css/sections/.  
3. **Concatenate and Minify**: All of these separate CSS files are concatenated into one large file, minified to reduce size, and given a unique "fingerprint" in the filename for cache-busting.  
4. **Final Output**: A single, optimized bundle.\[fingerprint\].css file is created in the public/css/ directory and linked in the \<head\> of every page on the website.  
5. **CMS Injection**: This same CSS file path is passed to CMS.registerPreviewStyle() in the admin configuration, telling DecapCMS to load it into the preview pane.

**Result**: Any style you write, whether for the whole site or a specific section, is automatically applied to both the live website and the CMS preview, guaranteeing visual consistency.

---

### **Step 4: Building the Website Pages**

This is the final step where Hugo renders the actual HTML pages.

1. **Trigger**: Hugo processes all markdown files in the content/ directory.  
2. **Identify Layout**: For a page that uses the page builder, its front matter will contain layout: advanced. This tells Hugo to use the layouts/\_default/advanced.html template.  
3. **Iterate Sections**: The advanced.html template reads the sections array from the page's front matter and loops through it.  
4. **Render Partials**: Inside the loop, for each section in the array, it uses the section's name (e.g., Testimonial) to dynamically call the correct HTML partial (layouts/partials/Testimonial.html). It passes all of that section's data from the front matter into the partial.  
5. **Assemble Page**: The partial renders its HTML. Hugo then assembles the HTML from all sections and places it within the site's base template (baseof.html) to create the final page.  
6. **Final Output**: The complete HTML file is written to the public directory, ready to be served.

By following these automated steps, the system ensures that adding, modifying, or removing a page section is a simple matter of managing a small, co-located set of files, with Hugo handling all the complex integration work at build time.
