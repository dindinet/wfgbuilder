# Modular Architecture for Page Sections

## 1. Concept Overview

Your proposed workflow transforms the Skill into a **Component Development Kit (CDK)**. Instead of injecting code directly into the monolith, developers use a separate, dedicated "Page Sections Library" repository. 

**The Workflow:**
1. Clone the `page-section-library` repo (which contains the Agent Skill).
2. Use the Agent Skill inside that repo to generate the 4 files for a new section.
3. Commit and push the repo.
4. In the target website's `hugo.toml`, import the `page-section-library` as a Hugo Module.
5. The Skill outputs the necessary `hugo.toml` module mount snippets for the developer.

---

## 2. Why This is a Great Idea

This approach perfectly aligns with enterprise-level frontend development:

*   **Reusability:** You can use the exact same page sections across 10 different client websites without duplicating code.
*   **Encapsulation:** The main website's source code remains pristine. It just consumes layout dependencies.
*   **Version Control:** If you fix a bug in the "Hero" section, you commit it to the module repo. All websites consuming that module can simply update their Hugo Module to pull the fix.
*   **Clean Development Environment:** When creating a section, the developer/AI is only looking at the component library, not fighting with the main site's complex routing or content.

---

## 3. Technical Challenges to Solve

While Hugo natively handles modules beautifully for layouts and CSS, **Decap CMS** will require some architectural adjustments to support a modular workflow. 

Here is what we need to solve:

### Challenge 1: Merging Decap CMS Configs
Decap CMS expects a single `static/admin/config.yml` file. If your module contains `data/decap/sections/hero.yml`, Decap won't automatically see it.
*   **Solution:** We must make the main site's `config.yml` dynamically generated by Hugo. Instead of a static file, we create `layouts/admin/config.yml` (as a Hugo template). This template will automatically loop through the `data/decap/sections/` directory (which Hugo Modules will merge automatically in memory) and dynamically render a unified `config.yml` on build.

### Challenge 2: Merging JS Previews
Decap CMS requires preview components to be registered in a single `cms.js` file (`CMS.registerPreviewTemplate`). If a module provides `MySectionPreview.js`, the main site's `cms.js` must import it.
*   **Solution:** We will use Hugo Pipes with JS Bundling (`js.Build`). We can have the main site's `cms.js` dynamically import all JS preview files that the Hugo Modules mount into the `assets/js/decap-previews/` directory.

### Challenge 3: Collecting Bespoke CSS
The main site needs to know about the bespoke CSS written in the module's `assets/css/sections/` folder.
*   **Solution:** Hugo Modules automatically merge the `assets` directories. As long as your main site's CSS pipeline uses globbing (like importing `sections/*.css` or using the existing `.Site.Store` collector), it will seamlessly bundle the module's CSS into the main site's stylesheet.

## 4. Updates Needed for the Agent Skill

To support this workflow, the final step of the Agent Skill must be modified to print out the integration instructions:

```markdown
### Installation Instruction
To use this new section in your main site, add the following to your website's `hugo.toml`:

[module]
  [[module.imports]]
    path = "github.com/your-org/page-section-library"

  [[module.mounts]]
    source = "layouts/partials/sections"
    target = "layouts/partials/sections"
  # (Include mounts for data, assets, etc.)
```

## 5. Conclusion

This is the optimal way to scale a Hugo site builder. It requires transitioning from "Static Decap CMS files" to "Hugo-Generated Decap CMS files", but the payoff in reusability and clean architecture is absolutely worth it.
